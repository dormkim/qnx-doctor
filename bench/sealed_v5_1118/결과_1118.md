- **우리 우위 = 정직성 축.** 종류 맞힘 10/12 vs naive 8/12이고, 그 격차 2점은 **전부 unknown 2/2 vs 0/2**이다: E11(CPU 스핀)·E12(세마포어 영구대기)에서 ours는 「메시지 교착이 아님(unknown)」이라고 **증명 가능한 범위 밖임을 선언**하고, naive는 「none」으로 흘려 못 맞힌다. deadlock·missing_reply는 네 arm 모두 만점(통제군).

## 정직한 흠 두 가지 (재채점하지 않음 — 봉인 1회)

1. **healthy 0/2는 채점기 어휘 문제다(실제 실패 아님).** 도구는 healthy 시나리오에 `none`(교착 없음)을 내는데, `score_structure.py`의 hit()이 그 `none`을 "healthy 적중"으로 세지 않는다(v4와 같은 none↔healthy 어휘 틈). **E09(정상 릴레이)는 ours가 정확히 `none`을 냈다** — 안전하게 건강으로 본 것이고, 표의 0/2는 과소계상이다. 봉인 후 변경 금지라 **스코어러를 고치지 않고 여기 기록만** 한다.

2. **E10의 "오경보 1건"은 탐지기 흠이 아니라 내 시나리오 설계 실수다.** E10의 "무해한 배경부하"를 **죽은 무한 스핀**(tick 1회 뒤 `for(;;)`)으로 짰다. 도구는 "이 프로세스가 매 스냅샷 RUNNING인데 루프가 진행 안 함 → spinning/unknown"이라고 **정당하게** 플래그했다(출력: `unknown (spinning): ... 204821(load) is running ...`). **교착·역전을 지어낸 게 아니다**(deadlock/chain 주장 0건). 공정한 설계는 부하가 주기적으로 진행(tick)하게 하거나 E10 라벨이 `unknown`을 허용하는 것. 다음 세트에서 교정한다.

## AI 층의 값어치
- **탐지·수정 모두 code 대비 기여 0**: 종류 code 10/12 = ai 10/12, 수정 ai 4/10 = naive 4/10 = naive_x2 4/10. 
- AI의 측정된 고유 값은 여전히 **"모른다고 말함 + 헛고침 0"**(false fix 0, unknown 2/2). 
- **send cycle(deadlock) 수정은 네 arm 모두 0/2** — 비동기 펄스로 바꾸는 수정이 어렵다(다음 레버).

## 결론
명제 「증명하는 AI + 모른다는 AI」가 **이번엔 숫자로 선다**: priority_chain 4/4 + unknown 2/2로 naive를 10:8로 이긴다. v4의 0/5는 탐지기가 아니라 하네스 버그였고(SEAL.md Correction 3), 그걸 고친 새 봉인 세트가 이를 증명한다. 남은 약점은 (a) AI가 code 대비 탐지·수정에서 더하는 게 없음 (b) send-cycle 수정 0/2 — 둘 다 다음 세트/레버의 과제.
